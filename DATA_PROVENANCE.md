# Payment Desk · data provenance

27 November 2026. Where every piece of financial data in this repository comes from, how it can be regenerated, what the identifiers in it are and are not, and what is not known. Facts that were checked are stated as facts; what rests on the authors' own account, or could not be established, says so.

## 1. Scope

Everything the application reads as financial data is in [`server/data/`](server/data) (42 tracked files) and in the test fixtures under [`server/test/`](server/test). There is no database, no import from another system and no network source: the files are the dataset. The application never contacts a bank, a supplier, a tax registry or an account-checking service.

## 3. How the synthetic data was written

Each document was composed to exercise one situation the firewall has to handle (a clean invoice, a changed account, a duplicate, an arithmetic error, two stated amounts, instruction-like text, an unknown vendor, a split, a missing field), in English, German, French and Spanish and in several layouts. Amounts were chosen to sit on purpose below, at or above the policy limits. Vendor records, history, purchase orders, callbacks and confirmations were written to match or deliberately contradict those documents.

Company names (Nordlicht Logistik, Atelier Lumière, Tulp Cloud, Iberia Office Supplies, Alpenstrom Energie, Adriatic Dev, Baltic Print, Pixelforge Media, Kestrel Retail) were invented. **Whether a company with one of these names exists was not checked, and some of them plausibly do.** Nothing here refers to such a company. Street addresses were invented but use real cities and postal codes. Every email address uses the reserved `.example` domain. There are no telephone numbers and no personal names.

## 4. Invoices as PDF: reproducible

`npm run fixtures:pdf` writes the eight PDFs from the descriptions in `server/test/pdf-specs.ts`. The output is deterministic, and `server/test/pdf.test.ts` regenerates every file and compares it byte for byte with the one in the repository on each test run. Five PDFs carry the same values as a text document of the same number; three are extra samples. `manifest.json` records each file's SHA-256, page count and size.

The provider lists were read on 27 November 2026 from https://docs.stripe.com/testing?payment-method=sepa-direct-debit and https://docs.adyen.com/development-resources/test-cards-and-credentials/alternative-payment-method-credentials through a page-reading tool that returned them as extracted text, not as a verbatim copy; each number used here also passes the checksum, which a transcription error would almost certainly break.

**Three numbers were replaced on 27 November 2026.** Until then the changed account in the fraud scenario, the account in the callback record and one account in a held-out document were numbers whose origin could not be established (`ES66 … 7891`, `DE02 … 2051`, `EE89 … 6011`). They were replaced by the provider test numbers above in every document, PDF, fixture and test. The first of them remains in one place: the two stored recordings read `INV-ES-55820` before the change, and a recording is never edited, so the document as it was then is kept in `server/data/recordings/documents/` for their replay only. The desk does not process that file.

What follows from this, stated plainly:

- **A valid checksum says a number is well formed. It says nothing about whether an account exists or whose it is.** Example IBANs use real bank codes, and a published example is not a guarantee that no such account exists. This repository does not claim that any of these accounts is non-existent.
- A provider's test number is the closest thing to an agreed sandbox account there is, which is why they are used where one exists. It is still a well-formed number with a real bank code; that a provider documents it for testing does not prove that no bank ever issued it.
- Nothing in the application can reach an account. Approval writes a JSON draft marked as sandbox; there is no bank connection, no payment file format a bank accepts, and no code path that sends anything.
- Numbers with a deliberately wrong checksum (for example `ES91 … 1333`) are used where a test needs an invalid account.

**BICs.** The BICs (`COBADEFFXXX`, `AGRIFRPPXXX`, `ABNANL2AXXX`, `CAIXESBBXXX`, `BKAUATWWXXX`, `NBHRHR2XXXX`, `HABAEE2XXXX`, `NWBKGB2L`, `EEUHEE2X`, `RZBSRSBG`, `BYLADEM1001`) are the public codes of real banks, matching the bank code inside the example IBAN they accompany. A BIC identifies an institution, not an account or a customer.

**Tax identifiers.** `DE811234567`, `FR12345678901`, `NL123456789B01`, `ESB12345678`, `ATU12345678`, `HR12345678901`, `EE101234567` are digit patterns written to look like the national format. They were not checked against any registry; a coincidence with a registered number is possible and not intended.

**Internal identifiers.** Vendor ids (`V-001`…), payment ids (`H-0001`…), purchase orders (`PO-7781`), callback and confirmation references (`CB-…`, `VC-…`), invoice numbers and payment references are invented and mean nothing outside this repository.

## 6. What "trusted record" means here

A trusted record is a row in one of the fixture files of section 2 that the sandbox treats as given. That is all the word claims.

| Record | What the application does with it | What it does not show |
|---|---|---|
| Vendor master | Compares the IBAN on a document with the IBAN in the row | That the account belongs to that company in the real world |
| Payment history | Looks for the same vendor and invoice number | That a payment was ever made |
| Callback record | Matches a typed reference to a row for that vendor and that exact IBAN | That anyone was called. The application places no call |
| Vendor confirmation | Matches a typed reference to a row for that vendor, invoice, currency and amount, with status `verified` | That a supplier was contacted. The application contacts no one; the "method" and "confirmed by" fields are fixture text |
| Policy | Supplies limits and rules to the controls | That these are any real company's limits |

In a real deployment these rows would come from an ERP, a bank file and a recorded verification process. Here they are files, and the README, the readiness report and the decision report say so.

## 7. Financial figures and calculations

| Figure | Origin |
|---|---|
| Gross, net, tax, currency, IBAN, invoice number of a payment | Read by an agent from the document and stored with the quoted line. Code then re-reads that line and checks that it contains the value; for a PDF the page and line come from the parser's source map |
| Per-payment limit, daily budget, split and duplicate windows | `policy.json`, as written amounts parsed into integer minor units |
| Arithmetic (net + tax = gross, line items = net) | Calculated in integer minor units; each calculation is a ledger entry with its method, inputs and result |
| Daily automatic total, exposure of a payment | Calculated from case state; the exposure points at the evidence of the gross amount |
| Blocked and waiting amounts, counts in the operational summary | `operationalSummary` in [`server/report.ts`](server/report.ts): summed per currency from the cases on the desk, never across currencies. The part that repeats an invoice already recorded is named separately. Not a prevented loss |

No figure that an agent states in prose is used for a decision. Amounts are held as integers in minor units.

**What "verified" covers, and what it does not.** For a value read from a document, code establishes four things: the reference exists, the quoted text is in the document at the stated place, the quote contains the value, and the value is normalised correctly. It does **not** establish that the line means what the agent says it means (a line item quoted correctly is still not the total), nor that the document is right. Field meaning is checked by controls such as arithmetic and the document's own labelled total line (a list of labels, so never complete) and by the second, independent reading; authority comes only from a trusted record. With the sixteen demo documents, 115 of 556 re-read values are critical to a decision and all 115 pass those four checks; 56 values cannot be checked by a program (30 dates, 20 agent statements, 6 quoted passages), none of them is critical, and none is counted as verified. An agent's sentence can never approve a payment: decisions come from the controls.

## 8. Scripted model answers

With no API key the agents' answers are fixed text from `server/test/fixtures.ts` and `server/test/showcase-responses.ts`. The orchestration, tools, controls and enforcement run for real; the words do not come from a model, and the interface says so on every screen. The scripted answers for the showcase documents were written after what hosted models returned on 26 November. They are not evidence of how a model reads an invoice.

## 10. Privacy and sandbox boundaries

- No real customer, supplier, employee or personal data. No real invoice. No real payment.
- No credentials in the repository: tracked files were searched for key patterns and private state on 27 November 2026; the only match is a placeholder string in a test. `.env`, saved desk state and logs are ignored by git.
- The server listens on the loopback interface and refuses requests from other hosts. With local inference, documents do not leave the machine.
- Nothing in this project is financial advice, and it is not a certified, audited or production system.

## 11. Public sources

None of the data comes from a public dataset. The external checks made for this document were the list of example IBANs at https://www.iban.com/structure and the test account numbers in Stripe's and Adyen's testing documentation (all read on 27 November 2026), used to see which of the account numbers are published examples or test numbers.

## 12. Known uncertainties

1. Four IBANs are believed to be widely published examples but were not confirmed against a primary source; the provider test numbers were read through a tool that returned extracted text (section 5). One number of unknown origin remains inside the document archived for the two stored recordings.
2. No IBAN here can be shown to belong to no one. The application cannot reach an account, which is the safeguard that matters.
3. Invented company names and tax-number patterns may coincide with real ones; this was not checked.
4. "Written by hand for this project" is the authors' statement, supported by the repository history, not by an independent audit.
5. The recordings describe earlier versions of the code.
